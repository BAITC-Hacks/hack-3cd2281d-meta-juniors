# Career Quest

Career Quest — веб-приложение для планирования развития сотрудников. Оно сопоставляет навыки сотрудника, его карьерную цель, требования следующего грейда и историю активностей, чтобы предложить подходящие шаги развития и объяснить выбор.

Проект создаётся для кейса Halyk Bank на HackAlem AI.

## Что входит в MVP

### Для сотрудника

- Просмотр своего профиля, навыков и карьерной цели.
- Получение от одной до трёх рекомендаций по развитию.
- Понятное объяснение каждой рекомендации: какой навык нужно развить, какое требование грейда он закрывает и как учитывается история активностей.
- Отметка выполненной активности и просмотр обновлённого прогресса.

Рекомендация должна учитывать несколько факторов, а не только самый низкий навык. Если подходящих активностей нет, приложение сообщает об этом и показывает незакрытые требования. Оно не придумывает активности или причины пропусков.

### Для HR

- Просмотр общих пробелов в навыках и участия в активностях.
- Доступ только к разрешённым HR-данным.

Сотрудник видит только собственный профиль и историю. Публичного рейтинга сотрудников в приложении нет.

## Как обновляется прогресс

После выполнения активности приложение начисляет указанный для неё прирост навыков. Уровень навыка не должен превышать ограничение активности или верхнее значение шкалы 5. Повторная отметка выполнения не должна начислять прирост второй раз. Обновление прогресса само по себе не означает автоматического повышения грейда.

## Тестовые данные

Для разработки и проверки используется синтетический стартовый набор:

- `employees.json` — профили сотрудников;
- `events.json` — активности и навыки, которые они развивают;
- `skills.json` — навыки и требования к ролям и грейдам;
- `activity_history.csv` — история участия, завершений и пропусков.

В матрице проверки указан набор из 200 профилей, 40 активностей, 60 навыков, 32 профилей требований и 2 743 записей истории. Перед демонстрацией сверьте эти количества с фактическим стартовым набором.

Используйте только синтетические данные. Не добавляйте в репозиторий реальные персональные данные сотрудников.

Приложение должно принимать дополнительные профили и связанную историю жюри в формате стартового набора без изменения кода.

## Основной сценарий демонстрации

1. Загрузить тестовый профиль и историю активностей.
2. Показать навыки сотрудника и выбранную карьерную цель.
3. Получить от одной до трёх рекомендаций.
4. Объяснить, как цель, требования грейда, пробелы в навыках и история повлияли на выбор.
5. Отметить активность выполненной и показать обновлённый прогресс.
6. Открыть HR-экран и показать общий срез компетенций.

Для демонстрации подготовьте обычный профиль и сложный проверочный профиль. Не заявляйте рост вовлечённости, завершения обучения или экономический эффект: это гипотезы, которые требуют отдельного пилота.

## Требования к проверке

- Интерфейс отвечает не дольше 2 секунд.
- AI-рекомендация формируется не дольше 10 секунд.
- Объяснение рекомендации соответствует данным профиля, требованиям и истории.
- Недопустимые для сотрудника активности не попадают в рекомендации.
- Права сотрудника и HR проверяются на сервере.
- Проект запускается по инструкции из этого README на другом компьютере.
- Проверка ключевого сценария не требует личного аккаунта участника или его личной платной подписки.

Подробная матрица проверок и фактические результаты ведутся в `docs/QA_REPORT.md`. Сценарий показа жюри можно расширять в `docs/DEMO.md`.

## Установка и запуск

Добавьте сюда проверенные команды после того, как команда зафиксирует структуру проекта. Инструкция должна включать установку зависимостей, настройку переменных окружения, применение миграций, загрузку стартовых данных и запуск приложения.

Для временной проверки Django-приложения с телефона в той же Wi-Fi-сети используется команда:

```bash
python manage.py runserver 0.0.0.0:8000
```

Откройте на телефоне `http://<IP-адрес-компьютера>:8000`. Для Django добавьте этот IP в `ALLOWED_HOSTS`. Для проверки экспертами подготовьте отдельный демонстрационный доступ или другой способ проверки без личных аккаунтов команды.

Не храните секретные ключи и пароли в GitHub. Добавьте в репозиторий `.env.example` без секретных значений и перечислите в нём только реально используемые переменные.
