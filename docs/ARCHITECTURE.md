# Career Quest: решения и ограничения

## Поток данных

JSON/CSV → Pydantic validation → preview → confirmation → atomic import → PostgreSQL → current skills → target gaps → eligible events → LLM selection → server validation → UI → development plan → work submission → HR review → recalculated skills.

В одном Django-приложении находятся серверные страницы и DRF API. Расчёты отделены от views: `quest/services/career.py`. AI-адаптер: `recommendations.py`. Импорт: `importer.py`. Интерфейс использует Django Templates, локальный Bootstrap grid и собственные CSS/JS. Внешних CDN-запросов при работе страницы нет.

## Актуальные навыки

`employees.skills` — результат последней аттестации. Хронологически применяются completed после `last_review_date`, до даты среза включительно. Для каждого эффекта:

`new = max(old, min(5, max_level, old + gain))`

База аттестации не перезаписывается при завершении, поэтому повторное вычисление не начисляет баллы дважды. Подтверждённый через приложение результат в день аттестации учитывается как результат после неё. В исходных self_paced-записях нет completed_at: поле date используется как приближение даты завершения; это ограничение исходного набора.

## Цель и допустимость

Явная career_goal приоритетна. При отсутствии предлагается следующий грейд той же роли; для Lead требуется выбор цели. Прогресс — доля покрытых уровней из целевого профиля, без обещания повышения.

Исключаются mandatory, неподходящие текущие role/grade, невыполненные prerequisites, отсутствие будущих сессий (кроме self_paced), уже запланированные, in_progress и completed. EV_036 допускает повтор в другую дату. Смена карьерной цели не отменяет ограничения аудитории мероприятия. Кандидат обязан реально сокращать хотя бы один разрыв к цели.

## AI и объяснимость

OpenAI Responses API, Structured Outputs, Pydantic. Настраиваемая модель, по умолчанию gpt-4.1-mini. LLM выбирает порядок и до трёх допустимых событий, а также факты, объясняющие выбор. Для каждого события объяснение обязательно включает разрыв навыка и историю. Сервер отвергает неизвестные/повторные event_id, выдуманные evidence_id, неподтверждённую критичность. Тексты фактов строятся сервером: модель не может подменить числа или придумать причину отказа.

В запрос входят роль, грейд, стаж, формат работы, цель, разрывы и агрегированные признаки кандидатов. Имена сотрудников, их ID и сырые строки истории не отправляются. `store=False`; это настройка хранения Responses, а не гарантия отсутствия любого хранения у провайдера. Все строки датасета считаются недоверенными данными.

Один запрос без автоматических повторов; сетевой timeout 7 с, ожидание результата максимум 8 с. Ограниченный пул из 4 потоков. При ошибке, отказе, истечении ожидания или провале валидации используется явно обозначенный подбор по правилам. Ожидание не блокирует загрузку страницы: браузер запрашивает рекомендации отдельно. Результаты кэшируются на 10 минут (резервные — на 1 минуту) с отпечатком данных, модели и версии правил.

Резервный балл: 10 × закрываемые уровни (критичный вес 4, остальные 1), поправки на долю завершений похожих мероприятий за 180 дней, пропуски/отказы/прерывания, совместимость с удалённой работой и нагрузку. Веса — эвристика команды, не критерии жюри и не обученная модель. Пропуски не являются абсолютным запретом. При пустом списке показываются причина и оставшиеся разрывы.

## Права и подтверждение результата

Сессии Django, CSRF для изменений. Employee видит только связанный профиль, запросы и работы. HR — отдельная группа без Django admin по умолчанию; видит команду и импорт, отвечает на запросы, проверяет присланные работы. HR не меняет цель, не добавляет шаг в чужой план и не отправляет работу за сотрудника. Самопроверка запрещена, даже если сотрудник входит в группу HR.

HR координирует развитие. Техническую практику содержательно проверяет компетентный руководитель или эксперт. В прототипе проверка реализована в общем HR-кабинете; отдельных назначений и роли эксперта нет. Эта граница прямо указана в интерфейсе.

Вход проверяет безопасный внутренний `next`; демо-кнопка открывает кабинет выбранной роли. Пароль можно временно показать, после ошибки он не возвращается в HTML. Выход — POST с CSRF. Истёкшая API-сессия возвращает `session_expired`; браузер предлагает повторный вход. Страницы 403/404 и устаревшая форма дают понятный путь восстановления без раскрытия чужого профиля.

Прямой endpoint завершения возвращает 409. Для завершения нужны начатый шаг, отправленная работа, все отмеченные критерии и комментарий HR. При возврате комментарий также обязателен. Процесс работает независимо от DEMO_MODE; этот флаг управляет демо-аккаунтами и кнопками входа.

Переходы выполняются в транзакции под блокировкой строки Employee. WorkSubmission хранит неизменяемую версию текста, ссылки и критериев. На один шаг допускается одна pending-версия. Номер предыдущей попытки защищает от устаревшей формы. Повторный просмотр/POST уже проверенной версии не меняет результат и не начисляет навыки повторно. Одобрение переводит связанную Participation в completed и сохраняет снимок изменений навыков и покрытия цели.

## Личный план

DevelopmentPlanItem хранит один текущий цикл на пару сотрудник/мероприятие: planned → in_progress → submitted → completed. Возврат на доработку: submitted → needs_revision → submitted. Запланированный шаг можно убрать (cancelled) и добавить заново. Повторное добавление и запуск идемпотентны. На старте создаётся in_progress-запись Participation; на завершении обновляется именно она. Пока она не completed, прироста навыков нет.

Начатые добровольные активности из импортированной истории синхронизируются с планом. Миграции переносят существующие in_progress и завершённые демо-операции из первой версии. История до использования приложения остаётся в профиле.

Смена цели сохраняет шаги. При запуске сервер повторно проверяет аудиторию, требования и пользу для актуальной цели. Уже начатое обучение можно завершить после смены цели: полученные навыки учитываются независимо от цели. Расчётные даты начала/завершения равны дате среза. Фактические времена отправки и проверки хранятся отдельно. Дата среза не ограничивает ручную проверку HR по расписанию будущих сессий; для производственного учёта требуется календарь и LMS.

## Практика и прогноз

DevelopmentRequest сохраняет потребность, исходный разрыв и цель на момент запроса; активный запрос на пару сотрудник/навык единственный. HR может закрыть запрос с объяснением или опубликовать персональное Event + PracticeBrief. Для System Design есть подготовленный командой кейс; для других навыков — шаблон, который HR должен конкретизировать. Это не сгенерированный AI курс и не исходное мероприятие организатора.

При публикации заново проверяется разрыв. Прирост и потолок не могут выходить за требования текущей цели. Персональная практика не доступна другим сотрудникам. Публикация не добавляет её в план автоматически. Утверждённое задание и история его выполнения защищены от перезаписи обычным импортом.

Сотрудник отправляет текст решения и необязательную HTTP(S)-ссылку. Содержимое ссылки не скачивается сервером. Для исходного каталога форма собирает отчёт о прохождении; учебные материалы отсутствуют. HR подтверждает критерии вручную — автоматической проверки артефакта моделью нет.

trajectory.py последовательно применяет эффекты начатых и допустимых запланированных шагов к копии навыков, учитывая потолки. Показывает прогноз покрытия цели и изменения навыков; в базу прогноз не записывается. Уже завершённые шаги не учитываются повторно. Это модель при успешном подтверждении всех шагов, а не оценка вероятности успеха.

Главный экран сначала показывает рекомендации из каталога, затем дополнительный фокус/практику и прогноз. Пустой подбор различает отсутствие цели, достигнутую цель, активный план и нехватку каталога; для каждого состояния указан следующий шаг.

## Предпросмотр импорта

Валидация и подсчёт новых/изменённых/неизменённых записей не записывают данные каталога, профилей или истории. Исходные файлы и результат проверки сохраняются в ImportDraft на сервере; браузер получает UUID. Черновик доступен только создавшему его HR, действует 30 минут, одно подтверждение выполняет весь импорт в транзакции. После подтверждения исходные файлы из черновика удаляются; остаётся сводка.

При подтверждении повторяются проверки, блокируются состояние набора и затронутые сотрудники. Отпечаток учитывает ревизию набора и прежние значения импортируемых записей; при изменениях нужен новый предпросмотр. Повторное подтверждение не повторяет импорт. Начатые через приложение PLAN_-записи и завершения с request_id защищены от перезаписи CSV. После отправки работы защищена также связанная импортированная запись участия; новые строки истории по индивидуальным практикам нельзя загружать в обход проверки HR. Старые черновики этого HR удаляются при следующем предпросмотре. CLI применяет импорт сразу, без интерактивного подтверждения.

## HR

Дефициты считаются относительно индивидуальных целей. Сигнал поддержки: за 90 дней нет добровольных завершений или есть ≥2 пропуска/отказа/прерывания. Это наблюдаемая эвристика для разговора, не прогноз увольнения и не диагноз. Список по ID; публичного рейтинга нет.

Подразделение, грейд и поиск ограничивают исходную выборку; дефицит конкретного навыка и сигнал поддержки вычисляются по актуальным навыкам и истории. Сводные показатели и список строятся по одной отфильтрованной группе. Ссылка на дефицит сохраняет остальные выбранные фильтры.

## Известные ограничения

- Русский интерфейс; названия навыков/мероприятий сохранены из английского каталога. Полной kk/ru-локализации нет.
- Нет интеграции с корпоративной LMS/SSO и доказательств реального влияния на вовлечённость.
- Повторные обязательные мероприятия сохраняются как в исходном CSV, хотя общее правило README запрещает повторы. Они не рекомендуются и не дают игровые награды.
- Локальная проверка 200 профилей не заменяет нагрузочное тестирование крупной организации.
- Работа реального AI зависит от действующего API-ключа, доступа к выбранной модели и сети. Резервный режим не подтверждает качество live-AI.
